# Google利用者認証とGitHub管理者認証

更新：2026-09-23。Manusの認証・API・ホスティング・ビルド環境を実運用の依存先にしません。画面はGitHub Pages、認証の本人確認はGoogle/GitHub、セッションと投稿DBおよび検証APIはSupabaseで運用する構成です。Supabase自体は外部依存として残ります。

## 要求した認証境界

一般の利用者登録、投稿、マイスポットの編集と削除はGoogle認証のみとします。オーナーと管理者の画面はGitHub認証に加え、変更されにくいGitHubの数値ユーザーIDを用いた許可名簿との一致を要求します。GitHubでログインしただけでは管理者にしません。Googleログインを管理権限へ昇格させません。パスワード・メールリンク・ゲストの投稿は認めません。閲覧は元の仕様を維持して公開しています。

## 認証元の確認

Supabaseは、同じ検証済みメールアドレスを持つOAuth identityを同じユーザーへ自動連携します。したがって、ユーザーIDやメールアドレスだけでGoogle利用者とGitHub管理者を区別する設計は避けます。[1]

標準JWTには `session_id` があり、`amr` の認証方法は `oauth` として表されます。OAuthの認証元を識別する専用の標準AMR値としてGoogle/GitHubが列挙されているわけではありません。[2]

このため、サーバー側でSupabaseのaccess tokenを `auth.getUser()` により検証し、GoogleまたはGitHubのプロバイダートークンも各社の本人情報APIへ照会します。その結果の識別子がSupabaseの信頼済みidentityと一致する場合に限り、セッションIDに結び付けた短期間の認証元記録を作成します。プロバイダートークンは保存・ログ出力しません。ブラウザの自己申告した役割や変更可能なuser metadataは権限の根拠にしません。

セッションの有効な認証元がGoogleである場合だけ投稿RPCを許可し、GitHubである場合はさらに許可名簿に登録されたowner/adminだけに管理用RPCを許可します。同じSupabaseユーザーへ両方のidentityが結び付いても、Googleセッションのまま管理権限を使わせません。検証記録の有効期間は1時間で、期限切れは再ログインを要求します。

## Google設定の公式要件

Google CloudのプロジェクトとGoogle Auth Platformのアプリ設定が必要です。Web applicationタイプのOAuth clientを作り、JavaScript originにはサイトのoriginだけを、redirect URIにはSupabaseの `/auth/v1/callback` を設定します。必要なscopeはopenid、email、profileです。追加のGoogleデータへのアクセスは要求しません。[3]

初期オーナー候補はリポジトリ所有者の `hiro-mochian`（GitHub数値ID `53967801`）です。名簿への追加は、この具体的なアカウントへのオーナー権限付与を確認してから行います。一般の管理者を自動登録する機能や、画面からの自己昇格機能は設けません。
